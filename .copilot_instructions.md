# Copilot Instructions for Karaoke Queue Project

## Prerequisites Before Any Code Changes

1. **Always inspect current state FIRST**
   - Run the server and test manually in browser
   - Check Rails console for database state
   - Verify routes are generating correctly
   - Look at actual error messages in server logs

2. **Never assume previous work is complete**
   - Each phase builds on prior work
   - Test every change before moving to next
   - Verify with actual HTTP requests, not just code inspection

## Development Workflow (MANDATORY)

### Step 1: Inspect Current State
```bash
# In terminal, run server and test these URLs:
rails server

# Test in browser:
GET http://localhost:3000/
GET http://localhost:3000/discover
GET http://localhost:3000/sign_in

# In Rails console, check data:
rails c
> Venue.all  # Check venues and their owner_id
> User.all   # Check users and their roles
> exit
```

### Step 2: Make ONE Logical Change
- Single controller update, OR
- Single view template, OR
- Single model method, OR
- Single route change
- Do NOT combine unrelated changes

### Step 3: Test The Change Immediately
Before moving to next change:
```bash
# 1. Verify Rails loads
rails runner "puts 'OK'"

# 2. Check for syntax errors in modified file
rails c < /dev/null

# 3. Test in browser with actual requests
# Note the exact URL, parameters, expected behavior

# 4. Check Rails server logs for errors/redirects
# Note in comments what you observed
```

### Step 4: Document What You Did
```ruby
# In code comments, write:
# Purpose: Why this change
# Tested: What was verified
# Status: Working / Blocked
```

### Step 5: ONLY THEN Move Forward
- Never assume "it probably works"
- Be skeptical of your own code
- Test unexpected paths (missing params, wrong roles, etc)

## Testing Checklist Before Committing

- [ ] Rails server starts without errors
- [ ] Welcome page loads (GET /)
- [ ] Can navigate to discover page (GET /discover)
- [ ] Can sign in (GET /sign_in)
- [ ] After sign in, can see queue page link
- [ ] Clicking queue page redirects properly
- [ ] All routes generate without errors
- [ ] No 500 errors in terminal
- [ ] No NameError or NoMethodError

## File Organization Rules

### Controllers
- One responsibility per controller
- Venue-related actions in `VenuesController`
- Song queue actions in `SongsController`
- Clear before_action hooks with authorization

### Routes
- Use `scope '/:venue_slug'` for scoped routes
- Nested routes use standard Rails conventions
- Always test routes: `rails routes | grep pattern`

### Views
- One template per action
- Use HAML consistently
- Include comments for role-based sections
- Test in browser after each view change

### Models
- Keep business logic in models
- Use enums for roles
- Document associations
- Test associations in rails c

### SCSS
- Import order: colors → tokens → everything else
- Use design tokens (variables)
- No hardcoded colors outside _colors.scss
- Test CSS compilation: `rails assets:precompile`

## Common Pitfalls to Avoid

1. **Route parameter mismatches**
   - If route has `:venue_slug`, path helper must include it
   - Example: `venue_songs_path(venue.slug)` NOT `songs_path`
   - Always check: `rails routes | grep pattern`

2. **Authorization without testing**
   - Add before_action but don't test with wrong role
   - Add owner check but test as non-owner first
   - Always test the negative case

3. **Database migrations without verification**
   - Run `rails db:migrate:status` after creating migration
   - Test `rails c` to verify schema applied
   - Check actual data: `Venue.first.inspect`

4. **URL generation errors**
   - Missing required parameters in links (this error happened twice!)
   - Generate routes, test them, THEN use in views
   - Check error: "missing required keys"

5. **Assuming views are correct**
   - Every template change = test in browser
   - Don't just read the HAML
   - Verify conditional logic works (hard refresh cache)

## When Things Break

### Debug Process
```bash
# 1. Read the actual error message carefully
#    "missing required keys: [:venue_slug]" = route param issue

# 2. Look at Rails server logs, not just browser
#    Server output shows exact line causing issue

# 3. Test in Rails console
rails c
> Song.all               # Check data state
> Current.venue          # Check context
> current_user.role      # Check auth

# 4. Test routes explicitly
rails routes | grep pattern

# 5. Check the code at the exact line mentioned
# Look at BEFORE and AFTER context
```

### Emergency Rollback
```bash
# If completely broken:
git status                          # See what changed
git diff filename                   # See exact changes
git checkout filename               # Revert one file
git reset --hard HEAD              # Revert everything

# Then restart testing from step 1
```

## Code Review Questions to Ask Yourself

1. Did I test this change in a browser?
2. Does this break any existing functionality?
3. Are all required parameters passed to route helpers?
4. Did I check the server logs?
5. Are there any hardcoded values I should parameterize?
6. Did I test as all three roles (owner, admin, performer)?
7. Is this change too large? Should I split it?
8. Did I verify the database actually has the data I'm querying?

## Example: Proper Workflow

**Goal:** Fix welcome page to use new routes

1. **Inspect**: 
   - Check current welcome page view
   - Test GET / in browser → see error
   - Check Rails logs → "missing required keys: [:venue_slug]"

2. **Change**:
   - Update view to use new route helpers
   - Add condition: is user logged in + has sesion venue?

3. **Test**:
   - Refresh browser → page should load
   - Click "Go To Queue" → should redirect if have venue
   - Click "Select Venue" → should go to discover
   - Check Rails logs → no errors

4. **Verify**:
   - Test as signed-out user → see sign in button
   - Sign in → see venue select
   - Pick venue → see queue page
   - Sign out → back to welcome

5. **Commit** (ONLY after above passes):
   - Clear description of change
   - Reference the route it uses

## Remember

- **Slow is fast**: Testing 2 minutes saves 30 minutes of debugging
- **Skepticism is your friend**: "I think this works" is not good enough
- **The browser doesn't lie**: If it errors in browser, code is broken
- **Server logs are truth**: Read them, don't guess
- **Test negatives**: Not just "what works" but "what breaks"
